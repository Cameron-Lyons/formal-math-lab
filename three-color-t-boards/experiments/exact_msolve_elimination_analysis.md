# Explicit linear elimination assessment

The existing reduced F2 model gives an exact, usable 96-variable input. Keeping all 80 original moments after substitution yields 172 nonzero generators. Physical elimination saves 8 bytes per stored exponent vector, and its larger potential benefit is avoiding transient monomials containing pivot variables. That algorithmic benefit is not benchmarked here; no solver was run for this note.

## What msolve currently does

In pinned msolve commit `cc044551f8e202d00691990fd3fd0b1226a88ea2`:

- `src/neogb/engine.c:95` sorts inputs by increasing leading monomial.
- `basis.c:254` makes each generator monic without substituting or eliminating variables.
- `f4.c:344` initializes the basis and S-pairs, and `symbol.c:198` picks pairs by minimum degree.
- `order.c:428` sorts DRL linear monomials as `x1 > x2 > ...`.

Variable order controls which variables become linear pivots, but msolve has no upfront variable-elimination pass and never shrinks `nvars`.

In natural cell order, the four unary moments lead with cells 0, 1, 2, and 3. Placing cells 0, 81, 90, and 99 first gives initial leading cells 0, 81, 90, and 90; the linear pair on cell 90 produces cell 99 as the fourth pivot. That matches the completed ordered trial's first log line (degree 1, 2-by-90 matrix, 1 new polynomial). The 100-variable exponent layout stays unchanged throughout.

## Exact reduced input

Before this analysis, we read and regenerated `exact_parity_math_fourier_reduced.json`. Its four linear pivot substitutions have 80, 17, 80, and 17 terms for cells 0, 81, 90, and 99. Each T placement contains at most one pivot, so substituting expands any moment term by at most 80 summands. Over F2, `L^2 = sum(z_i^2)`, and free exponents reduce modulo 3 using the retained free cubic domains.

Let `S` be the ordinary F2 polynomial ring on the 96 free cells. Substituting the four linear equations induces a quotient-ring isomorphism from the 100-variable ideal to the ideal in `S` generated by the substituted equations. To keep the exact quotient, you must include **all four substituted pivot domains** `L_p^3 + 1` alongside the 96 free domains `z_i^3 + 1`. There is no multiplier or normalization, and variables stay ordinary polynomial variables rather than Boolean ones.

The all-80 input drops eight zero equations (the four unary moments and their four Frobenius squares), leaving 72 moments, 4 pivot domains, and 96 free domains. ## Actual hash layout and expected memory saving

In `src/neogb/data.h:85`, `exp_t` is `uint16_t` (**2 bytes**). `hash.c:72` sets ordinary DRL vector length to `nvars + 1` (including total degree), and `hash.c:117` allocates `esz * evl * sizeof(exp_t)` bytes for the exponent slab. A 100-variable vector is therefore **202 bytes**. The earlier figure of 808 referred to **MiB for a full exponent slab at `2^22` slots**, not bytes per vector.

At `esz = 2^22`, a 100-variable hash table's principal arrays total roughly 936 MiB: 808 MiB for exponents, 64 MiB for `hd_t` metadata, 32 MiB for exponent pointers, and 32 MiB for the hash map (`hsz = 2 * esz`). A 96-variable table takes `776 + 64 + 32 + 32 = 904 MiB`. Explicit elimination therefore saves **32 MiB per table**, or **64 MiB if both tables reach `2^22` slots**. That ignores allocator overhead, matrix storage, and reallocation peaks, so it does not guarantee a 2-GiB fit. Because exponents are already 16-bit, a generic proposal to shrink them from 64 bits to 16 bits does not apply.

A separate allocation waste also stands out: the selective-import helper reserves slots for every referenced column before checking how many are already in the basis hash. In the natural-order degree-3 round, 95,359 referenced columns triggered a doubling from 131,072 to 262,144 even though only 148 monomials were actually new. The second ordered degree-4 round failed during that same conservative reservation (with the true new count unknown). Reserving space only for missing monomials is a more targeted fix than the constant 64 MiB saving, though it is not implemented here and would need separate validation.

## Recommendation

Explicit 96-variable F2 export is mathematically sound and keeps input growth bounded, but its direct memory saving is a modest constant. Any major gain must come from fewer F4 columns and new monomials, which must be measured rather than guessed from removing four variables. Keep the 136-generator and 172-generator variants separate, because the extra redundant equations in all-80 can change solver behavior without changing the ideal.
