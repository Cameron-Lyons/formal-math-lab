# Explicit linear elimination assessment

The existing reduced F2 model is an exact, usable 96-variable input. Retaining
all 80 original moments after substitution gives 172 nonzero generators.
Physical elimination removes eight bytes from every stored exponent vector;
its larger possible benefit is avoiding transient monomials containing pivot
variables. That algorithmic benefit is not established by an exact count or
solver benchmark here. No solver was invoked for this assessment.

## What the current solver does

In the pinned msolve commit `cc044551f8e202d00691990fd3fd0b1226a88ea2`,
`src/neogb/engine.c:95` sorts input by increasing leading monomial.
`basis.c:254` makes each input polynomial monic; it does not substitute or
eliminate variables. `f4.c:344` initializes this basis and its S-pairs, and
`symbol.c:198` selects pairs by minimum degree. DRL term sorting in
`order.c:428` places `x1 > x2 > ...` among linear monomials. Consequently
the variable order controls the leading variables of the linear subsystem,
but there is no separate up-front variable-elimination pass or shrinkage of
`nvars`.

With original cells ordered naturally, the four unary moments have leading
cells 0, 1, 2 and 3. With cells 0, 81, 90 and 99 listed first, their initial
leading cells are 0, 81, 90 and 90. The shared-90 linear pair supplies the
fourth leading variable 99. The linear subsystem's reduced DRL basis therefore
has pivots 0, 81, 90 and 99. The completed ordered trial's first log line,
degree 1 with a 2-by-90 matrix and one new polynomial, agrees with that source
analysis. The 100-variable exponent layout remains unchanged throughout.

## Exact reduced input

Read and regenerated `exact_parity_math_fourier_reduced.json` before this
analysis. Its pivot substitutions have 80, 17, 80 and 17 linear terms for
cells 0, 81, 90 and 99 respectively. Each T contains at most one pivot.
Substitution therefore expands a moment term by at most 80 summands;
characteristic two gives `L^2 = sum(z_i^2)`. Free exponents may then be reduced
modulo 3 using the explicitly retained free cubic domains.

Let `S` be the ordinary F2 polynomial ring on the 96 free cells. Substituting
the four linear pivot equations gives a quotient-ring isomorphism from the
100-variable ideal to the ideal in `S` generated by all substituted remaining
equations. This requires **all four substituted pivot domains** `L_p^3+1` in
addition to the 96 free domains `z_i^3+1`. There is no count multiplier or
normalization. These are ordinary polynomial variables, not Boolean ones.

| --- | ---: | ---: | ---: | ---: | ---: |
| Reduced 40 representatives | 96 | 136 | 11,884 | 13,186 | 25,262 |
| Reduced all 80 moments | 96 | 172 | 23,768 | 13,186 | 37,146 |

The all-80 input drops eight zero equations: four unary moments and their
four Frobenius squares. It retains 72 moment equations, four pivot domains,
and 96 free domains. Each 80-term pivot substitution contributes a 6,321-term
cubic domain; each 17-term substitution contributes 272 terms. The largest
equation has 6,321 terms. Maximum total degree is seven for the selected-40
input and eight for all-80.

A deterministic serialization omitting coefficient-one factors occupies
292,372 UTF-8 bytes for selected-40 and 477,211 bytes for all-80, with a
maximum line of 62,570 bytes in either. These sizes are for the serializer in
`exact_msolve_elimination_analysis.py`; other equivalent formatting can vary.
It reconstructs the existing reduced export and independently substitutes
all 80 moments from board geometry, confirming the Frobenius-derived partner
equations. No input file is submitted to a solver. Exact metrics and hashes
are in `exact_msolve_elimination_analysis.json`.

## Actual hash layout and expected memory saving

`src/neogb/data.h:85` defines `exp_t` as `uint16_t`: **two bytes**.
`hash.c:72` sets ordinary DRL vector length to `nvars+1`, including total
degree. `hash.c:117` allocates exactly `esz*evl*sizeof(exp_t)` bytes for the
contiguous exponent block. Thus the 100-variable vector is **202 bytes**.
The earlier figure of 808 refers to **MiB for a full exponent block at
2^22 slots**, not bytes per vector. Any 808-byte-per-vector statement is
incorrect.

At `esz=2^22`, a 100-variable hash reserves 808 MiB for exponent data plus
64 MiB for `hd_t` metadata, 32 MiB for exponent pointers, and 32 MiB for the
hash map (`hsz=2*esz`): approximately 936 MiB in the principal arrays.
A 96-variable hash reserves 776+64+32+32 = 904 MiB. Explicit elimination
therefore saves **32 MiB per hash**, or **64 MiB if both tables have 2^22
slots**. This excludes allocator and matrix overhead. It does not by itself
guarantee a computation will fit in 2 GiB; the failed growth can also require
reallocation peak memory. Exponents are already 16-bit, so a generic proposal
to compress them from 64 to 16 bits would be inapplicable.

A separate allocation issue remains visible: the selective-import helper
reserves slots for every referenced column before discovering how many are
already in the basis. The natural-order degree-three round doubled capacity
from 131,072 to 262,144 for 95,359 referenced columns but inserted only 148
new monomials. The second ordered degree-four round fails during that same
conservative reservation; the genuinely new count is unknown. Counting only
missing monomials, or expanding only for an actually new insertion, is a
more targeted future allocation change than the guaranteed 64 MiB saving.
It would need independent validation and remains unimplemented here.

Recommendation: explicit 96-variable F2 export is mathematically sound and
has bounded input expansion, but describe the direct memory reduction as a
modest constant saving. Any substantial improvement must be measured from
the resulting F4 columns and actual new monomials, not inferred from four
fewer variables. Keep the 136-generator and 172-generator variants distinct;
all-80 adds redundant equations and may change computational behavior without
changing the ideal.
